# terrain_raymarch_sv — GLSLレイマーチング山岳シェーダーのSystemVerilog移植

元のShadertoy風GLSL (fbmノイズ地形 + ソフトシャドウ + フォグ) を、
1ピクセルずつ計算する固定小数点FSMとしてSystemVerilogに移植したものです。

## ファイル構成 (Vivado/Quartus/GOWIN EDAへの追加順)

1. `rm_pkg.sv` (+ `sin_lut.svh`, `exp_lut.svh` を `include`)
   Q12.20固定小数点の共通ユーティリティ。sin/exp はcase文によるROM関数
   (これまでのILI9341プロジェクトと同じ「ROM-via-case」方式、`initial`ブロック不使用)。
2. `map_core.sv` — GLSLの `map(vec3 pos)` (fbm地形高さ関数) を1オクターブ/クロックで計算するFSM。
3. `isqrt.sv` — `normalize()` とガンマ補正 `sqrt(col)` 用の固定小数点sqrt FSM (桁ごと復元法)。
4. `fixed_div.sv` — `calcShadow` の `h*164.0/t` や `normalize` の逆数計算用の符号付き除算FSM。
5. `pixel_render.sv` — `mainImage()` 本体。レイ生成→地形マーチ(最大256回)→法線(map_core×6)→
   ソフトシャドウ(map_core×最大64, fixed_div×最大64)→ライティング→フォグ→ガンマ→RGB565量子化。
6. `frame_scan.sv` — 画面全体をラスタスキャンしながら `pixel_render` を駆動するトップモジュール。
   `pixel_valid` / `pixel_col` / `pixel_row` / `pixel_rgb565` を1ピクセルずつ出力するので、
   既存のST7789V/ILI9341 SPIドライバの書き込みシーケンスにそのまま接続できます。

## 検証状況 (iverilogでのシミュレーション)

- `rm_pkg` の `sin_fx`/`cos_noise`/`exp_neg_fx`: 実数計算との誤差を許容範囲内で確認済み。
- `map_core`: Pythonで再実装した「ビット完全一致」の固定小数点リファレンスモデルと
  **完全一致** (4パターン)。
- `isqrt_fx`: `math.isqrt` を使ったリファレンスと28パターンで**完全一致**。
- `fixed_div`: 符号付き除算のリファレンスと27パターンで**完全一致**
  (1つは極端な入力 `1.0/0.0001` で32bit固定小数点の表現範囲を超えてラップアラウンドする
  ケースですが、これはハードウェア・リファレンス双方で同じ挙動なので「バグ」ではなく
  Q12.20の表現範囲(約±2048)の制約です)。
- `pixel_render`: 空を見上げるレイでの出力が、手計算した期待値
  (`col=(0.7,0.8,1.0)*(1-0.5*rd.y)` → ガンマ → RGB565) と**完全一致**。
  地形にヒットするレイでも(march→法線→シャドウ→ライティング→フォグ→ガンマ)一連の
  ステートマシンがハングせず、妥当な値で完了することを確認。
- `frame_scan`: 4x2解像度・パラメータを縮小した設定でフルスキャンを実行し、
  `frame_done` まで正常に完走。左右対称の画角では空色ピクセルが完全に対称、
  地形ヒット部分ではノイズの非対称性を反映して微妙に異なる値になることを確認
  (いずれも期待通りの挙動)。

以上より、算術コアと制御フローは高い確度で正しいと考えていますが、
**実機(FPGA)での動作確認はまだ行っていません**。これまでのプロジェクト同様、
タイミング制約・リソース使用量・実機でのピン/クロック設定などは、
実際の合成・書き込みを通じた反復デバッグが必要になる想定です。

## 性能に関する重要な注意

このコードは「まず機能的に正しいベースライン」を目的としており、そのままでは
リアルタイム表示速度は出ません。

- 1ピクセルあたり最悪ケースで `map_core` 呼び出しが約326回
  (march 256 + 法線 6 + シャドウ 64)、各呼び出しが10クロック(NUM_OCTAVES=10)。
  さらに `fixed_div` 呼び出し(52クロック/回)がシャドウループで最大64回。
  → 1ピクセルあたり数千〜1万クロック程度。
- 320x240=76800ピクセル換算で1フレームあたり数億クロック規模になり、
  100MHz動作でも1フレーム数秒のオーダーです。

高速化の方向性 (次のステップとして想定):
- `NUM_OCTAVES` / `MARCH_STEPS` / `SHADOW_STEPS` パラメータを減らす
  (`frame_scan`/`pixel_render`のパラメータで調整可能)。
- `map_core` を複数インスタンス化してピクセルを並列処理する。
- `cos_noise` をパイプライン化し、`map_core`のオクターブループを
  1サイクル/オクターブより高速化する。
- シャドウループの除算を、除数tの範囲を絞ったLUTベースの近似に置き換える。

## 既知の制約

- Q12.20固定小数点 (32bit signed) のため、表現範囲は約±2048、精度は約2^-20。
  カメラのz座標 (`-iTime`) は時間経過で無制限に増加するため、長時間動作させると
  いずれこの範囲を超えます。実運用では `time_reg` を周期的にラップさせるか、
  より広いビット幅にするなどの対策が必要です。
- `fixed_div`/`isqrt_fx`/`map_core` はいずれも1ピクセル内で使い回す前提の
  単一インスタンスです(`pixel_render`内で排他的に順番に使用)。並列化する場合は
  インスタンスを増やすか、アービタを追加してください。
